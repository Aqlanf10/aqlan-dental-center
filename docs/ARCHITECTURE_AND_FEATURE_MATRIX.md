## 2. القرارات المعمارية التأسيسية (Modular Monolith Architecture)

1. **تطبيق موحّد مقسّم إلى وحدات واضحة (`Modular Monolith`):**
   - فصل صارم بين **نواة المجال النقية** (`src/finance`, `src/clinical`, `src/identity`, `src/settings`, `src/i18n`, `src/persistence`)، و**طبقة المنصة والقاعدة والهجرات** (`src/platform/db.ts`, `src/platform/migrations.ts`, `src/platform/idempotency.ts`, `src/platform/clock.ts`, `src/platform/crypto.ts`, `src/platform/sql/*`)، و**وحدات التطبيق** (`src/modules/governance`, `src/modules/patients`, `src/modules/appointments`, `src/modules/clinical`, `src/modules/billing`, `src/modules/lab-inventory`, `src/modules/backup`)، و**طبقة النقل والواجهات والمطبوعات** (`src/server/*`, `src/web/ui.ts`, `src/web/print.ts`).
   - يُمنع إنشاء ملف قاعدة بيانات مركزي متضخم؛ كل وحدة تملك استعلاماتها وقواعدها خلف واجهة صريحة.
2. **منسق معاملة واحد (`Single Transaction Coordinator`):**
   - يمتلك منسق المعاملة (`withTransaction`) اتصال PostgreSQL واحدًا فقط لكل عملية كتابة، ويمرر كائن المعاملة (`DbExecutor`) لجميع العمليات التابعة.
   - لا يُسمح لأي دالة مستودع فرعية بطلب اتصال جديد من الحوض (`pool.connect()` / `pool.query()`) أثناء احتجاز اتصال نشط، مما يمنع الاختناق الذاتي حتى على حوض صغير (`max = 2`).
   - أي خطأ أثناء `ROLLBACK` أو فك قفل استشاري أو غموض نتيجة `COMMIT` يؤدي إلى إتلاف الاتصال المعطوب (`client.release(true)`) بدل إعادته للحوض.
3. **مصدر واحد للهجرات وقفل التنفيذ وهوية القاعدة (`src/platform/migrations.ts` + `src/platform/sql/`):**
   - جدول `app_system_identity` يتحقق قبل أي كتابة من أن القاعدة المستهدفة مخصصة حصريًا لنظام `aqlan-dental-center` وببيئة معزولة مصرح بها.
   - قفل استشاري (`pg_advisory_lock`) يمنع سباق الهجرات المتزامنة، وجدول `app_schema_migrations` يتحقق من بصمة `SHA-256` لكل ملف هجرة ويرفض أي تعديل لاحق لملف مطبّق.
4. **هوية المريض وترقيم الملفات وبوابة المريض المستقلة:**
   - لكل مريض هوية داخلية ثابتة غير قابلة للتغيير (`patient_id`).
   - رقم الملف (`file_number`) مخصص للعرض والبحث؛ يبدأ ترقيم المرضى الجدد تلقائيًا من **`7000`** عبر متسلسلة ذرية (`app_patient_file_seq`) تمنع التكرار تحت التزامن العالي، دون تعديل تلقائي لأي أرقام أرشيف سابقة (`< 7000`)، مع حفظ سجل الأرقام السابقة عند أي تعديل إداري موثق للبحث والتدقيق.
   - حساب بوابة المريض (`patient_portal_accounts`) مصمم كهوية مصادقة مستقلة تمامًا عن `file_number` و`phone`، بوضع معطّل افتراضيًا (`DISABLED`) وآلية تفعيل واستعادة وإبطال جلسات آمنة، دون تفعيل حسابات حقيقية.
5. **الدقة المالية والترابط وعدم القابلية للمحو:**
   - جميع المبالغ تُخزَّن وتُحسب كأعداد صحيحة دقيقة بالوحدات الصغرى (`BigInt` عبر `src/finance/money.ts`) مقرونةً برمز عملتها (`YER`، `SAR`، `USD`) ولقطة سعر الصرف المعتمدة، دون أي استخدام لـ `floating point` ودون جمع عملات مختلطة.
   - سلسلة مراجع صريحة غير متنافسة: `خطة/اتفاق ← فاتورة وبنودها (مرتبطة بالإجراء لمنع تكرار الفوترة) ← سند قبض وتخصيصه ← جدول أقساط للمتبقي الفعلي`.
   - معادلة الأقساط تلتزم باحتساب المتبقي الحقيقي بعد طرح المقبوض الفعلي مرة واحدة (مثال القبول الإلزامي: إجمالي `2300`، مدفوع `500`، متبقٍ `1800` على `24` شهرًا = `75` شهريًا دون خصم الدفعة المقدمة مرتين).
   - السجلات المالية المعتمدة وسجلات التدقيق محمية بمشغلات PostgreSQL (`BEFORE UPDATE OR DELETE OR TRUNCATE`)؛ يتم التصحيح حصريًا عبر عمليات عكس/إلغاء مسببة وخاضعة للصلاحيات.
6. **المنع الافتراضي الخادمي ولوحة المالك الموحدة والإعدادات الفعّالة:**
   - كل طلب يمر بفحص خادمي حي يقرأ حالة الحساب ونسخة الصلاحيات الحالية من القاعدة دون الاعتماد على صلاحيات قديمة مخزنة في الجلسة.
   - إخفاء أي وحدة عن موظف يحجبها في الواجهة ويمنع الوصول لمسارات API والمطبوعات والمرفقات والتصدير التابعة لها في الخادم (`403`).
   - الطبيب المقيد (`own` أو `authorized`) لا يكتسب صلاحية الوصول لمريض بمجرد إنشاء موعد أو زيارة؛ يخضع الإسناد والإحالة والطوارئ لسياسة صريحة مسجلة في التدقيق.
   - حساب المالك الأساسي محمي من الإيقاف أو سحب صلاحية الإدارة العرضي تحت التزامن (`FOR UPDATE`).
   - كل إعداد تشغيلي (الدوام، الإجازات، الكراسي، العملات، العلامة المائية، صندوق الرسائل الصادرة) مربوط فعليًا بالوحدة المستهلكة له ومختبر أثره.
